= ESP Firmware Update over USB: Working HS-to-FS Process
:toc:
:toclevels: 3
:sectnums:

== Purpose

This document captures the currently working ESP firmware update process over the STM USB path.

The reliable flow is:

* Enumerate initially on the STM USB HS interface.
* Send an explicit STM FW API command to force the HS peripheral to re-enumerate as Full Speed.
* Reconnect from the PC utility after FS enumeration.
* Run the complete ESP ROM flashing sequence over FS.
* Send an explicit STM FW API command to restore HS after the update completes.

This flow avoids the observed STM HS bulk OUT instability with some 512-byte ESP FW update payload patterns while keeping the normal device connection on HS outside the update window.


== STM API Frame Format

All ESP FW update commands are sent using the display FW update API function `0xB1`.

[cols="1,1,3"]
|===
|Byte(s) |Meaning |Value

|0
|Packet type
|`0x02`

|1:2
|API length, little-endian
|For USB FW update, currently declared as `512` (`00 02`) so the fixed USB OUT frame is accepted consistently.

|3:4
|Sequence, little-endian
|Utility uses uint8 wrap in the low byte.

|5
|Function
|`0xB1` (`FW_UPDATE`)

|6:7
|Reserved
|`00 00`

|8
|Control byte
|High nibble = ESP FW sub-op, low nibble = `DISPLAY_UNIT` (`0x04`).

|9:10
|ESP SLIP length
|Only present for `API_ESP_FW_WRITE`.

|11..
|Payload
|Raw ESP SLIP frame for `API_ESP_FW_WRITE`, otherwise zero padding.
|===

=== ESP FW Sub-ops

[cols="1,1,2"]
|===
|Sub-op |Control byte |Meaning

|`0x00`
|`0x04`
|`API_ESP_FW_END`

|`0x01`
|`0x14`
|`API_ESP_FW_START`

|`0x02`
|`0x24`
|`API_ESP_FW_WRITE`

|`0x05`
|`0x54`
|`API_ESP_FW_USB_FORCE_FS`

|`0x06`
|`0x64`
|`API_ESP_FW_USB_RESTORE_HS`
|===

== Working Sequence

=== 1. Open Current USB Session

Connect to the GRL-PS's VID/PID (0x227F/0x0006). 

=== 2. Force the HS Peripheral to Re-enumerate as FS

The utility sends `API_ESP_FW_USB_FORCE_FS` before `API_ESP_FW_START`.

Sample TX, 512 bytes total, padding omitted:

[source,text]
----
API_ESP_FW_USB_FORCE_FS TX:
02 00 02 01 00 B1 00 00 54 00 00 00 00 00 00 00 ...

Meaning:
  02          packet type
  00 02       declared API length = 512
  01 00       sequence = 1
  B1          FW_UPDATE
  00 00       reserved
  54          sub-op 0x05, DISPLAY_UNIT 0x04
----

Sample RX:

[source,text]
----
API_ESP_FW_USB_FORCE_FS RX:
02 00 02 01 00 B1 00 00 54 00 00 00 00 00 00 00 ...
----

On STM, this dispatches through `disp_fw_upd_ctrl()` to `usb_runtime_force_fs()`, which sets:

[source,c]
----
g_usb_hs_force_fs_runtime = 1u;
----

The USBX app thread detects the flag change, drops the USB connection, re-runs the HS peripheral init with `PCD_SPEED_FULL`, and restarts the device without tearing down the USBX DCD.

=== 3. Utility Waits for FS Re-enumeration

After the force-FS response, the utility closes the stale HS handle and repeatedly opens the same VID/PID until the reopened device reports FS:

[source,text]
----
USB re-enumerated as FS (speed=2, EP1 OUT MPS=64).
----

Even though the API wire frame is still 512 bytes, USB FS transfers it as multiple 64-byte packets. This is working and is the intended update mode.

=== 4. Start the ESP FW Session over FS

Sample TX:

[source,text]
----
API_ESP_FW_START TX:
02 00 02 02 00 B1 00 00 14 00 00 00 00 00 00 00 ...
----

Sample RX:

[source,text]
----
API_ESP_FW_START RX:
02 00 02 02 00 B1 00 00 14 00 00 00 00 00 00 00 ...
----

On STM, `esp_fw_session_start()`:

* Optionally drives ESP BOOT/RESET if `ESP_FW_GPIO_BOOT_CTRL` is enabled.
* Flushes stale UART RX packets.
* Clears stale unified API queue data.
* Sets `g_esp_fw_active = 1`.

== ESP ROM Flash Command Flow

After `API_ESP_FW_START`, every ESP ROM command is wrapped in `API_ESP_FW_WRITE`.

The current working USB update uses:

* Runtime baud: `115200`.
* ESP `FLASH_DATA` block size: `256` bytes.
* USB FLASH_DATA pacing: `0 ms`.
* STM response length: actual response payload length, not always 512 bytes.

=== ESP ROM Packet Format inside API_ESP_FW_WRITE

The ESP ROM packet before SLIP encoding is:

[source,text]
----
direction: 1 byte   0x00 for request
opcode   : 1 byte
length   : 2 bytes little-endian
checksum : 4 bytes little-endian
payload  : length bytes
----

The utility SLIP-encodes that ESP packet, then sends:

[source,text]
----
API bytes 9:10  = SLIP length, little-endian
API bytes 11..  = raw SLIP encoded ESP packet
----

=== SYNC

SYNC payload is:

[source,text]
----
07 07 12 20 followed by 32 bytes of 55
----

Sample TX, sequence shown as `03 00`; padding omitted:

[source,text]
----
API_ESP_FW_WRITE SYNC TX:
02 00 02 03 00 B1 00 00 24 2E 00
C0 00 08 24 00 00 00 00 00
07 07 12 20
55 55 55 55 55 55 55 55 55 55 55 55 55 55 55 55
55 55 55 55 55 55 55 55 55 55 55 55 55 55 55 55
C0
...

Meaning:
  24          API_ESP_FW_WRITE control byte
  2E 00       SLIP length = 46 bytes
  C0 ... C0   ESP SYNC SLIP frame
----

Sample RX, length varies with ESP ROM response:

[source,text]
----
API_ESP_FW_WRITE SYNC RX:
02 <len_lo> <len_hi> 03 00 B1 00 00 24
C0 01 08 04 00 07 07 12 ... C0
----

The embedded ESP response starts with:

[source,text]
----
C0 01 08 04 00 ...
----

where `01` is ESP response direction and `08` is the SYNC opcode.

=== READ_REG

The utility reads ROM register `0x40001000` to detect the ESP chip.

Sample unescaped ESP payload:

[source,text]
----
00 10 00 40
----

Sample response prefix:

[source,text]
----
C0 01 0A 04 00 <value_le32> ... C0
----

where `0A` is the READ_REG opcode.

=== SPI_ATTACH

Sample TX, padding omitted:

[source,text]
----
API_ESP_FW_WRITE SPI_ATTACH TX:
02 00 02 06 00 B1 00 00 24 12 00
C0 00 0D 08 00 00 00 00 00 00 00 00 00 00 00 00 00 C0
...

Meaning:
  0D          ESP SPI_ATTACH opcode
  08 00       ESP payload length = 8
  payload     00 00 00 00 00 00 00 00
----

Sample RX:

[source,text]
----
API_ESP_FW_WRITE SPI_ATTACH RX:
02 13 00 06 00 B1 00 00 24
C0 01 0D 04 00 00 00 00 00 C0
----

=== SPI_SET_PARAMS

The utility sends the current flash geometry:

[source,text]
----
0, 4MB, 64KB sector, 4KB sector, 256 byte page, 0xFFFF
----

This is sent as ESP opcode `0x0B`.

=== FLASH_BEGIN

For a firmware size of `1203984` bytes, flash offset `0x10000`, and 256-byte blocks:

[source,text]
----
num_blocks = ceil(1203984 / 256) = 4704
block_size = 256
offset     = 0x10000
----

Sample TX, padding omitted:

[source,text]
----
API_ESP_FW_WRITE FLASH_BEGIN TX:
02 00 02 08 00 B1 00 00 24 1E 00
C0 00 02 14 00 00 00 00 00
10 5F 12 00
60 12 00 00
00 01 00 00
00 00 01 00
00 00 00 00
C0
...

Meaning:
  02             ESP FLASH_BEGIN opcode
  14 00          ESP payload length = 20
  10 5F 12 00    firmware size = 1203984
  60 12 00 00    block count = 4704
  00 01 00 00    block size = 256
  00 00 01 00    flash offset = 0x10000
  00 00 00 00    encrypt flag = 0
----

Sample RX:

[source,text]
----
API_ESP_FW_WRITE FLASH_BEGIN RX:
02 <len_lo> <len_hi> 08 00 B1 00 00 24
C0 01 02 04 00 00 00 00 00 C0
----

=== FLASH_DATA

Each `FLASH_DATA` command writes one 256-byte block.

ESP `FLASH_DATA` payload layout:

[cols="1,2"]
|===
|Bytes |Meaning

|0:3
|data length, little-endian. Usually `256`.

|4:7
|block sequence number, little-endian.

|8:11
|reserved, zero.

|12:15
|reserved, zero.

|16..
|firmware data bytes.
|===

Checksum is computed over firmware data bytes only, not over the 16-byte `FLASH_DATA` sub-header.

Sample TX prefix for one block, padding omitted:

[source,text]
----
API_ESP_FW_WRITE FLASH_DATA TX:
02 00 02 62 00 B1 00 00 24 <slip_len_lo> <slip_len_hi>
C0 00 03 <esp_len_lo> <esp_len_hi> <checksum_le32>
00 01 00 00
5B 00 00 00
00 00 00 00
00 00 00 00
<256 firmware data bytes>
C0
...

Meaning:
  03             ESP FLASH_DATA opcode
  00 01 00 00    data length = 256
  5B 00 00 00    block sequence = 91
----

The utility log now prints FLASH_DATA success every 1024 blocks plus the final block to reduce UI overhead:

[source,text]
----
Block 1024/4704 OK ...
Block 2048/4704 OK ...
Block 3072/4704 OK ...
Block 4096/4704 OK ...
Block 4704/4704 OK ...
----

=== FLASH_END

The utility sends ESP `FLASH_END` with reboot flag `0` so the ESP exits ROM flashing and boots normally.

Sample ESP payload:

[source,text]
----
00 00 00 00
----

== End Session and Restore HS

After ESP flashing completes, the utility sends `API_ESP_FW_END` over FS.

Sample TX:

[source,text]
----
API_ESP_FW_END TX:
02 00 02 <seq> 00 B1 00 00 04 00 00 00 00 00 00 00 ...
----

Sample RX:

[source,text]
----
API_ESP_FW_END RX:
02 00 02 <seq> 00 B1 00 00 04 00 00 00 00 00 00 00 ...
----

Then the utility sends `API_ESP_FW_USB_RESTORE_HS` while still connected over FS.

Sample TX:

[source,text]
----
API_ESP_FW_USB_RESTORE_HS TX:
02 00 02 <seq> 00 B1 00 00 64 00 00 00 00 00 00 00 ...
----

Sample RX:

[source,text]
----
API_ESP_FW_USB_RESTORE_HS RX:
02 00 02 <seq> 00 B1 00 00 64 00 00 00 00 00 00 00 ...
----

On STM, this dispatches to `usb_runtime_restore_hs()`, which clears:

[source,c]
----
g_usb_hs_force_fs_runtime = 0u;
----

The USBX app thread detects the flag change, performs a visible soft disconnect, re-runs the HS peripheral init with `PCD_SPEED_HIGH`, and restarts the device without calling `HAL_PCD_DeInit()`.

The utility then closes the stale FS handle and waits for HS:

[source,text]
----
USB re-enumerated as HS (speed=3, EP1 OUT MPS=512).
----

== Error Responses

`esp_fw_write_cmd()` sends short API responses for STM-side errors:

[cols="1,2"]
|===
|Payload |Meaning

|`FF`
|STM timed out waiting for an ESP UART response.

|`FE`
|STM rejected the ESP FW write request because the API/slip length was invalid or UART TX failed.
|===

Example timeout response:

[source,text]
----
02 0A 00 <seq> 00 B1 00 00 24 FF
----

Example reject response:

[source,text]
----
02 0A 00 <seq> 00 B1 00 00 24 FE
----

== Notes and Constraints

* The update intentionally runs the ESP ROM protocol at `115200` baud in this working path.
* `esp_fw_write_cmd()` does not perform baud-rate handling.
* USB HS is used only before and after the firmware update window.
* During the update window, the STM HS peripheral is forced to FS on the same connector/ULPI path.
* Host-side fixed 512-byte API OUT writes are still used; FS transports them as multiple 64-byte USB packets.
* STM WRITE responses use the actual response length and are not padded to 512 bytes.
* The working data block size is 256 ESP firmware bytes per `FLASH_DATA` command.
